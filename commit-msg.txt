fix: /api/admin/backtest 4-minute timeout/crash blocking nightly pipeline

User reported /picks-history failing again after nightly tasks ran. Root
cause: logs showed the pipeline aborted at the Run Backtest step with a
500 - every step after it (including the new Refresh Reliability
Calibration step) never ran that night.

Reproduced live: POSTing /api/admin/backtest directly took 233 seconds and
failed with a Cloudflare 520 from Supabase's own edge (the origin giving up
on an overly-long-running request). Same root bug class as the /accuracy
fix (full jsonb predictions payload selected across the whole table), plus
a novel one specific to this route: it re-fetched and RE-SCORED every
completed race's predictions from scratch on every run forever, the exact
"no incremental skip" bug already fixed once for the predict retrospective
route (2026-09-06) but never ported here.

Fix, iterated and re-measured against real data at each step:
1. Narrow the SELECT + bounded-concurrency batching: 233s -> 53s, but then
   hit a genuine correctness bug - upserting a body missing NOT NULL
   columns (race_id etc, the whole point of narrowing) throws
   "null value in column race_id violates not-null constraint". Postgres
   validates NOT NULL against the full proposed INSERT tuple even when the
   ON CONFLICT DO UPDATE path is actually taken.
2. Switched to plain per-row .update() (only touches given columns) in
   small concurrent batches, plus split predictions into
   scored/unscored so only genuinely-new predictions get the expensive
   full-field fetch+recompute+write - already-scored rows fold their
   cumulative stats in from the already-stored actual_results instead.
   First attempt split this into two separately-filtered queries
   (actual_results IS NULL vs IS NOT NULL) - the NOT NULL query alone
   still hit a genuine Postgres statement timeout even with narrow
   columns, because the WHERE filter itself (combined with IN(100 ids))
   was the expensive part to plan, not the payload.
3. Final fix: one unfiltered query per chunk, splitting scored/unscored in
   JS after the fact, with a small follow-up fetch (by id) for only the
   genuinely-unscored subset. Live-verified: 200 OK, 77s, 25807
   predictions scored, only 280 needed fresh computation out of ~33000
   total rows.

Manually ran the missed /api/admin/reliability-refresh afterward to catch
up (racesAnalyzed: 3285) since the aborted pipeline never reached it.

Verified: npm test (247/247), npm run lint (clean), npm run build (clean),
plus live end-to-end checks of /accuracy, /picks-history, and / (home)
all returning 200 against a fresh server instance.
